# Notification Hooks (send/ack/response) — Design Spec

**Date:** 2026-09-25
**Status:** Approved for implementation planning
**Author:** dolufemi (with Claude Code)
**Tracking:** [NOT-41](https://linear.app/notifyjs/issue/NOT-41/notification-persistence-and-ackresponse-hooks)

## 1. Summary

Extend `@netiflyjs/core` with lifecycle hooks so a consuming app can persist
notifications when they're sent, and react when a client acknowledges or
responds to one. This is a new capability: today Notifly is strictly
server → client (a `send()` call pushes a payload down the wire) and never
reads anything a client sends back. This spec adds a client → server
direction (ack/response) and the hook points needed to observe both.

This directly extends the v1 design's stated non-goal of "Delivery
acknowledgement / read receipts" (see
[2026-09-24-notifly-design.md §3](./2026-09-24-notifly-design.md)) — that
exclusion is superseded by this spec.

## 2. Goals

- Let a consuming app persist a record of every notification sent, without
  Notifly itself owning any storage (stays storage-agnostic, same
  philosophy as `resolveUserId` being auth-agnostic).
- Let a client acknowledge a notification (delivery/read receipt) with no
  payload of its own.
- Let a client send an app-level response tied to a notification (e.g. the
  user clicked "Accept" on a friend request), carrying an arbitrary
  JSON-serializable payload.
- Sync ack/response across a user's other live connections (multi-tab,
  multi-instance) so all of a user's devices reflect the same state.
- Never let a hook failure, or a malformed client message, block delivery,
  crash the process, or leave a connection in a bad state.

## 3. Non-goals

- Notifly does not persist notifications itself, and does not validate
  that an acked/responded `id` corresponds to a notification it actually
  sent (it doesn't track sent state at all) — that validation, if wanted,
  is the consuming app's responsibility inside its own hook handler, using
  its own persisted record.
- No deduplication of the echo a client receives of its own ack/response
  (see §6).
- No rate limiting or message-size limits on client → server messages.
- No delivery/read receipts distinguishing "sent," "delivered," and "seen"
  beyond what `'sent'` and `'ack'` already express — that distinction, if
  wanted, is layered by the app on top of these two events.

## 4. Breaking changes

This is a breaking change to the wire protocol and to `send()`'s return
type, and ships as a new major version of `@netiflyjs/core` (and
`@netiflyjs/express`, which re-exports the same types).

- **Wire envelope**: clients previously received the raw
  `JSON.stringify(payload)` you passed to `send()`. They now receive
  `{ "type": "notification", "id": "<uuid>", "payload": <payload> }`.
  Any existing client-side code reading the raw payload directly must be
  updated to unwrap `.payload`.
- **`send()` return type**: changes from `Promise<void>` to
  `Promise<string>` (the generated notification id).

## 5. Wire protocol

**Server → client** (existing push, now enveloped):

```json
{ "type": "notification", "id": "<uuid>", "payload": <your payload> }
```

**Client → server** (new — the first client-originated messages Notifly
ever reads):

```json
{ "type": "ack", "id": "<uuid>" }
{ "type": "response", "id": "<uuid>", "payload": <any JSON> }
```

**Server → client relay** (an ack/response echoed to the user's other
connections, see §6):

```json
{ "type": "ack", "id": "<uuid>" }
{ "type": "response", "id": "<uuid>", "payload": <any JSON> }
```

The relay frame has the same shape as the client → server frame that
triggered it — a receiving client doesn't need to distinguish "my own ack
echoed back" from "a different tab's ack," since both are equally valid
signals to update local UI state (e.g. clear a notification badge).

`id` is always generated by Notifly inside `send()` (`crypto.randomUUID()`)
and returned to the caller. Notifly does not track or validate ids past
generating them — see §3.

## 6. Server-side flow

All three message kinds reuse the existing `notifly:user:<id>` Redis
channel — no new channels, no change to the subscribe-on-first-connection /
unsubscribe-on-last-disconnect lifecycle in
[connectionRegistry.ts](../../../packages/core/src/connectionRegistry.ts).
The published JSON payload now always carries a `type` field, and every
instance's Redis subscriber callback branches on it:

- **`send(userId, payload)`**:
  1. Generate `id`.
  2. Emit `'sent'` locally on the calling instance:
     `{ userId, id, payload }`.
  3. `PUBLISH` `{ type: 'notification', id, payload }` to
     `notifly:user:<userId>` (unconditional, exactly as today).
  4. Return `id`.
  5. Every subscribed instance's callback sees `type: 'notification'` and
     forwards to its local sockets for that user — unchanged from today's
     `deliverLocally`, just now unwrapping the envelope.

- **Client sends `{ type: 'ack', id }` or `{ type: 'response', id, payload }`**
  on its own socket:
  1. The instance holding that socket parses the frame.
  2. If valid, it emits `'ack'` (`{ userId, id }`) or `'response'`
     (`{ userId, id, payload }`) locally — **exactly once**, on this
     instance only.
  3. It then `PUBLISH`es a relay frame (§5) of the same shape to
     `notifly:user:<userId>`.
  4. Every subscribed instance's callback (including the originating one,
     since Redis fans the publish out to all subscribers of that channel)
     sees `type: 'ack'`/`'response'` and **only forwards to local sockets**
     — it never re-emits the hook event. The hook event already fired
     once, synchronously, in step 2, before the publish.

This keeps the "one Redis channel per user, subscribe only while you hold
a connection" model completely unchanged, and keeps hook-firing decoupled
from fan-out: fan-out can reach N connections across M instances, but the
hook itself always fires exactly once per client action, on the instance
where that action physically arrived.

**Accepted behavior**: the client whose ack/response triggered the relay
will also receive the relayed frame back on its own socket (an echo of its
own action). This is not deduplicated in v1 — a client already knows it
sent the ack, so receiving it back is a harmless no-op to ignore.

## 7. Public API (`@netiflyjs/core`)

```ts
interface NotiflyInstance {
  send(userId: UserId, payload: unknown): Promise<string>; // id, was Promise<void>

  on(event: 'connect' | 'disconnect', listener: (userId: UserId) => void): this;
  on(event: 'sent', listener: (info: { userId: UserId; id: string; payload: unknown }) => void): this;
  on(event: 'ack', listener: (info: { userId: UserId; id: string }) => void): this;
  on(event: 'response', listener: (info: { userId: UserId; id: string; payload: unknown }) => void): this;
  on(event: 'error', listener: (error: Error) => void): this;
  once(...): this; // mirrors on() for all events above, as today

  disconnect(userId: UserId): void;
  close(): Promise<void>;
}
```

Usage:

```ts
notifly.on('sent', ({ userId, id, payload }) => {
  db.notifications.insert({ id, userId, payload, status: 'sent' });
});

notifly.on('ack', ({ userId, id }) => {
  db.notifications.update(id, { status: 'read' });
});

notifly.on('response', ({ userId, id, payload }) => {
  db.notifications.update(id, { status: 'responded', response: payload });
});
```

## 8. Error handling

- A throwing/rejecting `'sent'`, `'ack'`, or `'response'` listener is
  caught and reported via the existing `emitError` path (the same
  listener-count-gated `'error'` emit already used for Redis/connection
  failures) — it never blocks or fails the `send()` call, the ack relay,
  or any other listener.
- A malformed client message (invalid JSON, missing/unknown `type`,
  missing `id`) is dropped — no hook fires, no relay is published — and
  reported via `'error'` (per user decision, for operator visibility into
  misbehaving clients). The connection is not closed for a single bad
  frame.
- All other error handling from the v1 design (§11 of
  [2026-09-24-notifly-design.md](./2026-09-24-notifly-design.md)) is
  unchanged.

## 9. Testing

- `notiflyServer.test.ts`: real WS round-trips — a client sends `ack`/
  `response`, assert the corresponding hook fires exactly once, and a
  second connection for the same user (simulating another tab or another
  instance) receives the relay frame.
- `redisRouter.test.ts`: extend pub/sub tests for the `type`-discriminated
  message shape (`notification` vs `ack` vs `response`).
- New case: a malformed client message asserts `'error'` fires and the
  connection stays open and otherwise functional.
- Existing `connectionRegistry.test.ts` and `heartbeat.test.ts` are
  unaffected — the subscribe/unsubscribe lifecycle and heartbeat logic
  don't change.

## 10. Migration notes (for CHANGELOG / release)

- Bump `@netiflyjs/core` and `@netiflyjs/express` to a new major version.
- Document the envelope change and `send()` return-type change as breaking
  in the changelog, with a before/after snippet for client-side unwrapping.
- README gets a new section documenting `'sent'`/`'ack'`/`'response'` next
  to the existing `'connect'`/`'disconnect'`/`'error'` documentation, plus
  a client-side example of sending `ack`/`response` frames.
